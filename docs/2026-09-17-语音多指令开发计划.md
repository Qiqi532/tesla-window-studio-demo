# 语音多指令（一句话多动作）开发计划与可行性分析

> **范围边界：** 本文档只做计划与可行性分析，不修改任何源码、测试或配置。所有代码示例均为"建议签名/伪代码"，实施时再落地。

## 1. 结论先说

能做，而且主要工作量在**解析层与分发层**，识别层基本不用改。

当前链路是"识别整句 → 规范化 → `parseCommand` 只产出**一条**标准命令 → `commandDispatcher.execute` 只派发**一条** → `VehicleController.dispatch` 只执行**一条**"。长句被截断到第一条，根因是 `parseCommand` 的线性 `if/else` 链在第一个命中的部件类别就 `return`，以及 `commandDispatcher`/`VehicleController` 都是单命令接口，没有任何"切分 + 顺序执行 + 汇总"逻辑。

建议方案：**在 `parseCommand.js` 新增 `parseCommands(text) → { commands, errors }`，按连词/标点/停顿把整句切成子句，每句复用现有 `parseCommand` 独立解析；`commandDispatcher.execute` 改为对 `commands` 顺序派发、逐条收集结果、合并成一条反馈文案返回**。识别层保持现状（不截断），仅在语音层把"逐条播报"改为"合并播报"。该改法不触动 `parseCommand` 与 `execute` 的单命令行为，现有 54 项测试可继续通过。

## 2. 现状分析：长句为什么只执行了第一条

完整链路：`nativeRecognition.js / localRecognition.js`（识别整句）→ `transcript.js normalizeTranscript / selectTranscriptCandidate`（规范化+候选去重）→ `parseCommand.js parseCommand`（整句→单条）→ `commandDispatcher.js execute`（单条→单字符串）→ `vehicleController.js dispatch`（单条→单结果）。

逐条根因（均基于真实代码）：

1. **解析层单点返回**：`parseCommand.js:57-108` 的 `parseCommand` 是一串 `if (PART_TERMS.window.test) … else if (trunk) … else if (door) … else if (light)`，命中第一个类别就 `return standardCommand(...)`。整句被当成一条命令。
   - 例：`打开左前车门和后备箱，然后打开大灯` → `trunk` 分支在 `parseCommand.js:75` 先命中（正则包含"备箱"），返回 `{type:'set-trunk', targets:['trunk'], value:1}`，左前车门与大灯被整段丢弃。
2. **单返回值结构**：`parseCommand` 成功只返回 `{type, targets, value, originalText}`，失败只返回 `{error, originalText}`，**没有任何数组/多命令形态**，结构上就排除了"多条"。
3. **分发层单命令**：`commandDispatcher.js:19-38` 的 `execute` 只调用一次 `parseCommand`、只 `vehicle.dispatch` 一次、只 `return` 一个字符串，没有循环。
4. **车辆层单命令接口**：`vehicleController.js:540-569` 的 `dispatch(command)` 接收**一个**标准命令对象、返回**一个**结构化结果 `{ok, changed, code, detail, message}`，无批量入口。顺序依赖（如开三门后某动作需门已关）只能靠逐条执行自然体现，但当前根本到不了这一步。
5. **规范化抹掉分隔符**：`transcript.js:17` `normalizeTranscript` 用 `PUNCTUATION` 把逗号、顿号、句号全部删掉。所以"切分"必须在**规范化之前**对原始文本做，不能在已去标点文本上切。
6. **候选歧义守卫**：`transcript.js:63-68` 当不同候选映射到不同有效命令时返回 `ambiguous-transcript`。对整句而言，各 alternative 是同一句的微小变体，`validCommands.size` 通常为 1，故不是当前阻塞点；但若实施时把每个子句当独立候选喂入，该守卫会误杀合法多指令，需规避（见 §4）。
7. **识别层本身不截断**（非根因，但有限制）：`nativeRecognition.js:93-95` 设 `continuous=false`、`maxAlternatives=3`，返回的是整句最终文本；`localRecognition.js:40` 录音上限 `maximumMs=6000`、`asr.worker.js:66` `chunk_length_s:6`，约 6 秒以内整句可被 Whisper 完整转写。像"打开左前车门和后备箱，然后打开大灯"（约 3–4 秒）识别层能给出完整文本。真正风险是 Whisper tiny 对长句/无标点句的准确率下降（见 §3）。

一句话混合多类别（门+箱+灯）被丢弃，是上面 1–4 共同导致的；而同类多目标（如"关闭雾灯和尾灯"）其实**已经能工作**：`parseCommand.js:98` 的 `LIGHT_TARGETS.filter(... pattern.test(command))` 会把 fog 与 tail 都收进 `targets`，返回 `{type:'set-light', targets:['fog','tail'], value:0}`。这说明"同类多目标"无需切分，"跨类别多动作"才需要切分。

### 2.1 用户示例的逐层推演（以"打开左前车门和后备箱，然后打开大灯"为例）

- 识别层：原生/本地识别均返回整句文本 `打开左前车门和后备箱，然后打开大灯`（不截断）。
- `normalizeTranscript`：删标点 → `打开左前车门和后备箱然后打开大灯`。
- `selectTranscriptCandidate`：各 alternative 变体解析为同一首条命令，`validCommands.size===1`，返回该候选文本。
- `parseCommand`（现状）：`trunk` 分支命中 → **仅**返回 `{type:'set-trunk', targets:['trunk'], value:1}`，门与大灯丢失。
- `commandDispatcher.execute`：派发上面这一条，`vehicle.dispatch` 开后备箱，返回 `已打开后备箱。`。
- 结果：用户听到只开了后备箱，门与大灯无反应——与实测"后面的动作不执行"完全吻合。

实施后的目标推演：

- `parseCommands`：逗号切出 `打开左前车门和后备箱` 与 `然后打开大灯`；第二段去"然后"前缀得 `打开大灯`；第一段经跨类别兜底再拆为 `打开左前车门`（set-door FL）与 `打开后备箱`（set-trunk trunk）。
- `execute` 顺序派发三条：`set-door[FL]`→`已打开左前车门。`、`set-trunk[trunk]`→`已打开后备箱。`、`set-light[headlight]`→`已开启前大灯。`，合并为 `已打开左前车门、后备箱，已开启前大灯。` 一次播报。

## 3. 可行性分析：哪些是解析层问题，哪些是识别层问题

**解析层（可完全解决，无外部依赖）**
- 单点返回、单返回值、单命令分发、单命令车辆接口——全部是纯前端逻辑，可控。新增 `parseCommands` + 顺序执行即可覆盖绝大多数用户长句。

**识别层（部分解决，受模型能力限制）**
- 不截断整句：已具备，无需改。
- 长句准确率：Whisper tiny q8（`asr.worker.js` 固定权重）对 6 秒内长句尚可，但超过 ~6 秒会被 `localRecognition.js` 强制停录，且 tiny 模型对无标点长句容易吞字/串词。浏览器原生识别（`nativeRecognition.js`）对长句表现依赖厂商服务，质量参差但一般也会给整句。
- 标点恢复：tiny 与多数原生服务**不返回标点**，因此"按逗号切分"不可靠，切分必须主要依赖**词汇连接词**（然后/接着/再/同时/和/跟/以及）与**空白/换行**，而非标点。
- 候选歧义：`selectTranscriptCandidate` 的 `ambiguous-transcript` 是针对"不同识别假设"，不是针对"多指令"；实施时若把整句作为单候选送 `execute`、由 `parseCommands` 内部切分，则该守卫不会被触发，保持现有行为。

**结论**：解析层 100% 可行；识别层无需为"多指令"改动架构，只需在语音层把逐条播报合并为一条，并提示用户长句尽量用连接词/逗号。识别准确率下降属模型固有风险，通过"宁可少执行也不误执行"的保守切分原则兜底。

## 4. 推荐方案设计

### 4.1 切分规则（子句边界）

在 `parseCommands` 内对**原始文本**（未去标点）先做切分，再对每子句调用 `parseCommand`：

- **强分隔符（必切）**：逗号 `，`、顿号 `、`、分号 `；`、句号 `。`、换行、连续空白。
- **时序连接词（必切，且作为分隔标记消费）**：`然后`、`接着`、`再`、`同时`、`之后`、`完了`、`先…再/然后`。
- **并列连接词（默认不切，作为同类多目标的合并信号）**：`和`、`跟`、`以及`、`与`、`并`、`并且`。
  - 取舍：`关闭雾灯和尾灯`、`打开前备箱和后备箱` 应保留为**一条多目标命令**（现有逻辑已支持）；`打开左前车窗和副驾车窗` 也应为一条 `set-window [FL,FR]`。因此并列连接词**不作为切分点**，让 `parseCommand` 的 `.filter` 收集同类多目标。
- **易误切场景与兜底**：
  - `打开左前车门和后备箱`（跨类别、无逗号）：仅按上面规则不会切，会落入 `trunk` 分支丢门。兜底策略（阶段二增强）：若某子句被 `parseCommand` 命中某一类别后，残留文本仍含**其他类别关键词**（车门/车窗/灯/备箱/天气），则在并列连接词处再次切分该子句，使每个类别各成一条。该兜底有串词风险，遵循"宁可少执行也不误执行"——只在并列连接词明确存在时才切，无连接词则保守保留单条并提示。
  - 用户示例"打开左前车门和后备箱，然后打开大灯"含逗号，阶段一即可在逗号处切成 `打开左前车门和后备箱` + `然后打开大灯`；第二段去"然后"前缀后解析为大灯。第一段若启用兜底则进一步拆出门与箱。

`splitClauses` 参考实现（阶段一仅做分隔符+时序词切分，跨类别兜底为阶段二增强）：

```js
const SEP = /[，,、；;。.\n\s]+|然后|接着|再|同时|之后|完了/g
function splitClauses(text) {
  return String(text ?? '')
    .split(SEP)
    .map((s) => s.replace(/^(?:请帮我|麻烦|请|帮我|我要|我想要)+/, '').trim())
    .filter(Boolean)
}
```

注意：分隔正则已包含空白与标点，故 `splitClauses` 在**去标点前**对原始文本运行；切出的子句再交给 `parseCommand`（其自身会二次去标点与去前缀），保证与现有单命令解析完全一致。阶段二的跨类别兜底在 `splitClauses` 之外、对单子句做二次 `parseCommand` + 残留关键词扫描后，于并列连接词 `和|跟|以及|与` 处再切一次。

### 4.2 数据结构

新增 `parseCommands(text)`：

```js
// parseCommand.js 新增导出（parseCommand 保持原签名不变）
export function parseCommands(text) {
  const clauses = splitClauses(String(text ?? '')) // 见 4.1 规则
  const commands = []
  const errors = []
  for (const clause of clauses) {
    const result = parseCommand(clause) // 复用现有单命令解析
    if (result.error) errors.push({ ...result, clauseText: clause })
    else commands.push({ ...result, clauseText: clause, index: commands.length + 1 })
  }
  return { commands, errors }
}
```

每条子命令携带：`index`（序号）、`clauseText`（原文片段）、`type/targets/value`（标准命令）、执行后填入的 `result`（来自 `VehicleController.dispatch`）、`feedback`（该条反馈文案）。

`commandDispatcher.execute` 的返回结构**保持为字符串**（向后兼容），内部改为：

```js
async execute(text) {
  const { commands, errors } = parseCommands(text)
  const parts = []
  for (const cmd of commands) {
    const result = cmd.type === 'set-weather'
      ? await this._runWeather(cmd)          // 复用现有天气分支
      : vehicle.dispatch({ type: cmd.type, targets: cmd.targets, value: cmd.value })
    parts.push(result.message ?? describeCommand(result))
  }
  for (const err of errors) parts.push(ERROR_MESSAGES[err.error] ?? ERROR_MESSAGES['unsupported-command'])
  return parts.join('') // 或按 4.5 合并为自然句
}
```

### 4.3 执行策略

- **顺序执行**：按子句顺序逐条 `dispatch`，后一条看到前一条已更新状态，避免并行竞态（现有 `VehicleController` 状态机天然支持中途反向，如先开后关）。
- **部分失败继续**：某条失败（如 `missing-position`、`driving-control-not-supported`）只把该条的错误文案计入汇总，其余照常执行，**不做整体回滚**（各 `dispatch` 相互独立且幂等，无需事务）。
- **互锁与依赖冲突**：
  - 行驶控制仍按项目既定决策**仅限页面按钮**，`parseCommand.js:103-105` 对档位/速度正则返回 `driving-control-not-supported`，因此"挂D档"类子句天然映射为错误条目，不会误触互锁；其余子句照常执行。
  - 因为语音不控制档位，**支持范围内不存在会互相阻断的批内互锁**（车门/箱/窗/灯之间无互锁）。仍须保留 `VehicleController` 的逐条拒绝（如极端情况下 `door-locked-while-driving`），失败即计入汇总、不回滚。
  - 同目标反向（"打开车窗然后关闭它"）：顺序执行后末态为关，视为"末态优先"，不特殊回滚。
- **去重与幂等**：同一目标重复出现（"打开左前车窗"两次）→ 第二条 `dispatch` 返回 `changed:[]`、文案"车窗已经处于该状态"，无害。识别层重复候选由 `selectTranscriptCandidate` 已去重，多指令不改该路径。

关键原则：**绝不修改 `parseCommand` 与 `execute` 的单命令入参/返回语义**，仅在其上叠加多命令能力，从而 54 项现有测试零改动通过。

### 4.5 反馈与播报汇总

- 不刷屏：`runCommand`（`voice.js:142-152`）原本每条 `execute` 返回即 `feedback`+`speak` 一次；多指令下 `execute` 返回**一条合并文案**，`feedback`/`speak` 仍只调用一次。
- 中文合并：成功条用顿号/`、`连接主语、共用动词，例如 `已打开左前车门、后备箱，已开启大灯。`；失败条追加 `（车门需补充位置；行驶控制仅支持按钮）`。
- 播报前 `synthesis.cancel()`（`voice.js:132`）保留，避免旧队列叠加。

## 6. 风险与取舍

| 风险 | 取舍/处理 |
|---|---|
| 识别层长句准确率下降（tiny 无标点、>6s 截断） | 切分靠连接词而非标点；提示用户用逗号/然后；识别失败由现有错误文案兜底，不强行猜测 |
| 切分歧义导致误操作 | 遵循"宁可少执行也不误执行"；并列连接词默认不切，跨类别兜底仅在明确连接词处才切 |
| 播报刷屏 | 合并为单条文案、单次 `speak`、前置 `cancel` |
| 性能 | 多指令仅多次调用现有同步 `dispatch`，开销可忽略；天气为唯一 `await`，仍顺序 |
| 替代方案（不做多指令） | 保持单命令但改进提示与示例，成本最低但无法满足用户"一句话控全车"的核心诉求；仅在多指令误触发率不可接受时回退 |

| 6 | 打开左前车窗，然后关闭它 | 先开后关，末态关 |
| 7 | 打开车门 | 仅 `errors`：`missing-position`，不误开全部门 |
| 8 | 打开左前车门，然后挂D档 | 门开；`挂D档`→`driving-control-not-supported` 错误条，不进入档位 |
| 9 | 播放音乐，打开大灯 | `播放音乐`→`unsupported-command`；大灯仍开 |
| 10 | 切换雨天，打开后备箱 | 进雨天道路、后备箱开 |
| 11 | 打开左前车门和副驾车窗 | 门 FL 开、窗 FR 开（跨类别兜底切分） |
| 12 | 打开全部车门，关闭左后车门 | 四门开，再单独关 RL |

**判定标准**：1–6、10–12 全部目标执行且只播报一次；7、8、9 中不支持/需补充的子句被明确拒绝且不波及其余子句；无任何"误开全部车门/误挂档"类误操作。
