# 3D 车模控制 Demo：可行性与准备状态

调查日期：2026-09-15。本文件记录当前阶段的发现，不代表完整实施计划。

## 作业边界

原始截图要求：高还原 3D 车模、拖拽旋转、点击控车、语音控车；交付可运行 demo、Vibe Coding 过程录屏和有价值的中间产物。网页是允许的形态。现有作战手册提出了更多部件与页面细节，后续计划时再取舍。

## 可行性判断

纯前端网页可覆盖展示、旋转、点击和状态驱动动画。建议使用 Vite、TypeScript、Three.js 和原生 HTML/CSS 作为第一版候选栈：Three.js 的 `OrbitControls` 负责视角，`Raycaster` 负责拾取，`GLTFLoader` 加载 glTF/GLB，统一车辆状态层把点击、面板和语音指令转换成相同的动作。Three.js [官方加载器文档](https://threejs.org/docs/#GLTFLoader)已在浏览器打开核对；该文档说明它加载 glTF 2.0，压缩模型可能还要对应解码器。

语音候选是浏览器 `SpeechRecognition`/`webkitSpeechRecognition` 加中文指令解析，配合文字指令入口。其实际识别可用性取决于目标浏览器、麦克风权限和识别服务，应在开发早期于本机 Edge 做真实口语验证；当前没有完成此验证。文字入口可在识别不可用时继续验证控制链路。若识别服务不稳定，再评估本地识别或服务端方案及其部署成本。

开源车模可提升外观，但许可和可动部件结构必须逐个核实。优先寻找有独立车窗、车门节点或动画的 glTF/GLB；加载后遍历节点树、检查模型尺寸、材质、纹理和枢轴，再确定映射表。一个整体网格无法直接实现真实的窗玻璃升降，可能需在 Blender 中拆件和重新设枢轴。现阶段未下载、未核验任何候选车模的许可证或节点结构，因此不能承诺某个开源资产可直接用。准备模型时需保存来源、作者、许可证和署名方式，避免将代码仓库的许可证误认为模型资产许可证。

有两条可讨论的路线：先选高质量、可拆件的开放许可车模并实现控制；或先用可控的简化模型验证点击、状态、语音，再接入高质量车模。你的“车模用开源车模”偏好使前一条更贴近目标；最终仍需以实际资产巡检结果决定。原生 TypeScript/Three.js 减少 UI 框架负担；若后续需要复杂面板或组件化，可再比较 React + React Three Fiber 的维护成本。

## 需要准备和验证的资源

1. 核对 FlClash 当前节点或配置的 HTTPS 出站是否正常；经 `7890` 测试 GitHub 和 npm 时，代理返回 HTTP CONNECT 200，但 TLS 随即断开。GitHub 的 OpenSSL 握手报 `unexpected eof while reading`，`gh api rate_limit` 报 EOF；切到“全局”模式复测仍失败，随后已恢复原“规则”模式。网络恢复后再测试 GitHub 和 npm registry 连通性。
2. 网络连通后重新运行 `gh auth status`；若仍显示凭据无效，再刷新或重新登录 GitHub CLI，确认仓库创建权限。不要把令牌写进项目文件。
3. 选定一款开放许可车模，保存许可证和作者信息，核验车窗节点、纹理、文件体积和真实比例；需拆件时再安装 Blender。
4. 在 Edge 的本地 `localhost` 页面实测 WebGL 帧率、鼠标/触屏拾取、麦克风授权和中文语音识别；当前只有浏览器安装验证。
5. 用 Win+G 试录一次桌面、浏览器和麦克风，确认过程视频能覆盖要求；录制文件不纳入源码仓库。

这些待验证项会决定最终模型路线和语音技术。当前尚未初始化网页工程，也没有可运行 demo。
